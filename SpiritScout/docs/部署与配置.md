## 控制台登录（可选）

**默认不开登录**：`web.auth_mode: none`，本机打开就是工作台，没有密码提示；
即使工作区里还留着 `admin.db`，也不会重新把界面锁上。

要开登录就两步（`password` 模式）：

```bash
.venv/bin/python -m spiritscout --set-admin-password      # Windows 换 .venv\Scripts\python.exe
launch.cmd --auth password                                # 或把 web.auth_mode 改成 password
```

- `--auth none|password` 只影响本次启动，不改配置文件。
- 选了 `password` 但还没设密码：本机照常起服务并按开放模式运行，只提示一句。
- 想彻底清掉凭据：`python -m spiritscout --clear-admin-password`（删账号，不动会话密钥）。
- **监听非回环地址**（`0.0.0.0` 等）时默认仍要求先启用登录，否则拒绝启动；确实要在
  内网裸奔再把 `web.remote_auth_required` 设为 false。远程访问请在反向代理上配 HTTPS。

设密码时只把 scrypt 加盐哈希写进工作区的 `admin.db`（容器里是数据卷）；明文不进
命令行、不写日志、不落盘。**密码长度不设限制**——一位的口令和整句话都收，只有
「空密码 = 不设密码」这一条。在交互终端里设完，明文会在**那个终端显示一次**，方便
当场记下来；之后重启、`/api/auth/status`、日志与界面都不再显示它。
自动化可以用 `--password-stdin` 从标准输入喂密码（这条路不回显，避免明文跟着
stdout 进日志），或 `--admin-username` 指定用户名；同名账号会被覆盖。

`.env` 里的 `SPIRITSCOUT_ADMIN_USERNAME` / `SPIRITSCOUT_ADMIN_PASSWORD`（旧版
`SPIRITSCOUT_SERVER_PASSWORD`）仍然支持，启动时同步进 `admin.db` 且**优先级更高**
——它会覆盖在本机设的那份密码，覆盖时日志里有一条 WARNING 点名。不想被覆盖就删掉
这两个环境变量，或设 `SPIRITSCOUT_ADMIN_SYNC=0` 关闭启动同步。

## 模型调用与依赖兼容

模型网关固定使用 LiteLLM `1.102.0`，MCP SDK 约束为 `>=1.28.1,<2`。
LiteLLM 较新的 MCP 支持面向 2.x，不要单独升级这一项。

### 自定义 OpenAI 兼容渠道

任何按 OpenAI 协议提供 `/v1/chat/completions`（含工具调用）的渠道都能直接接入，不需要
LiteLLM 侧的特例。在 `configs/models.yaml` 里声明供应商与模型，**密钥不写进 YAML**：

```yaml
providers:
  - name: my-channel
    provider: openai_compatible
    base_url: https://api.example.com/v1
    api_key: ""                              # 留空：密钥在控制台「模型」页填
    api_format: chat_completions

models:
  - model: "vendor-model-name"               # 端点认什么名字就写什么
    provider_ref: my-channel
    capabilities: [reasoning, code, chinese, security]
    context_window: 131072
    reasoning_effort_levels: []
    cost_input_per_mtok: 0.0
    cost_output_per_mtok: 0.0
    rate_limit_rpm: 60
    max_concurrency: 0                       # 端点并发上限，0/省略 = 不限
    quality_score: 0.95
```

- **本地单槽端点必须写 `max_concurrency: 1`**：LM Studio 用 `--parallel 1` 加载、
  llama.cpp 单实例，都只有一个槽。不写这个值，一轮十几个任务会同时打到端点，
  每个都排在队列里耗到硬超时（实测：辅助调用 90s 超时、会话卡住不动）。
  写了之后并发请求排队，排队时间不计入单次调用硬超时，只会变慢不会失败。

- **密钥怎么来**（三处，优先级从高到低）：
  1. 控制台「模型」页给供应商填 key —— 加密存进本机密钥库，**推荐**，填一次以后不用再管；
  2. `configs/models.yaml` 里直接写 `api_key`（不推荐，明文落盘）；
  3. 环境变量兜底：`SPIRITSCOUT_LLM_KEY_<供应商名大写>`（如 `SPIRITSCOUT_LLM_KEY_MY_CHANNEL`），
     或通用的一条 `SPIRITSCOUT_REMOTE_LLM_KEY`。值不落盘、不进审计，适合临时试用。
- **没有密钥也能启动**：控制台照常起来，只有发任务/连通性测试才会报缺凭据，
  到「模型」页填上即可。密钥库里有记录时会覆盖 YAML 与环境变量，方便随时换 key。
- **停用而不是删掉**：某个模型想暂时退场（换回别家额度、避峰、先放着以后再看），
  在「模型」页点「停用」，或手写 `enabled: false`：

  ```yaml
  models:
    - model: "vendor-model-name"
      provider_ref: my-channel
      enabled: false                          # 配置留着，但不参与选用
  ```

  停用后它从编队候选、命名链、路由挑选和会话启动里一并消失，画像与供应商绑定
  原样保留；点「启用」或删掉这一行即可恢复（缺省即启用，YAML 里只在停用时才
  留这一行）。指派与命名链校验共用同一份过滤结果，所以「指派了已停用的模型」
  会被当成「指派了已删除的模型」一样拒绝，不会静默绑定。连通性测试仍能看到
  停用项——先测通再启用是正常顺序。
- 模型名带冒号（如 `cn:deepseek-v4.1-flash`）时用引号包住；网关会自动补 LiteLLM 的
  `openai/` 前缀，按 `base_url` 路由。
- 其他配置项里引用的 `${SOME_VAR}` 占位符**没设置仍然启动失败并指名缺哪个**——
  这条是按"不制造空地址或空凭据"保留的；只有模型密钥例外，它不再走占位符。
- `is_fallback_for: [主模型]` 声明备机；主模型连续失败时按注册表顺序切换。
- **模型优先级＝「模型」页那条命名链的顺序**（写进 `configs/agent_models.yaml`
  的 `naming`）：链上第一条就是路由首选，取不到才按链往下走，链外模型排最后。
  指派的 Agent 仍以指派为准。改完**不用重启**——下次开工（或写手类功能调用）
  会自动重读 `models.yaml` 与编队表；只有文件写坏时才保留上一份可用清单。
- 子 Agent 面板里每个实例后面显示「模型 · 渠道」，渠道是该模型的供应商/base_url；
  这一行由 `GET /api/sessions/{id}/agents/models` 按审计尾部算出，打开旧会话也看得到。

**经验怎么才算「新的」？** 入库前会比一遍库里最近两千条有效经验（去空白标点后的编辑相似度），达到 `experience.duplicate_threshold`（默认 0.95）就取消这条结果、只留一条审计 `experience.near_duplicate`，其余照存。想让同义句也进来就调到 1.0（只挡完全同文）；注意这是入库闸门，与「经验」页的二次提炼互不影响——提炼的相似度默认 90%，在页面上改（50%–100%，改完记住上次的值），而且必须先看到提炼稿、点「保留」才会写库和删原件。

**模型优先级多久生效一次？** 「模型」页排的优先级链由网关运行期重读，间隔取 `gateway.priority_refresh_seconds`（默认 30 秒，允许 5~3600）。所以改完顺序不必重启服务：正在跑的会话下一批调用就按新顺序走；会话页另有一个只作用于单个会话的模型下拉，改完立刻生效（`POST /api/sessions/{id}/model`，空值 = 回到优先级链）。
- **密钥只存在密钥库里**，`models.yaml` 里不要写；服务启动、热重载、写手类功能都会
  自动注入。本机端点（`localhost` / `127.0.0.1` / `*.local`）不需要密钥，会用占位值
  `sk-local` 调用；远端端点没有密钥时会被排到链路末尾，全链失败会直接提示去
  「模型」页补 key。
- 只保留一个可用模型时，任何调用失败都会直接暴露原因，不会悄悄换到没配好的备机。

连通性测试会让模型只回复 `ok`，显示请求完成耗时；它不覆盖任务里的流式输出和工具请求。
若测试成功、任务却立即失败，请查看完整错误，而不只看界面截断的 `APIConnectionError`。

例如 `cannot import name 'CacheableResult' from 'mcp.types'` 是本地依赖不兼容，
会在请求路径初始化时失败；修改密钥或反复测试网络不会解决它。按照项目约束重新安装，
或执行 `python deploy.py up` 重建镜像。仅重启旧镜像不会更新依赖。

依赖升级前需验证真实 SDK 的普通请求、流式输出、工具参数和 MCP 连接。
仓库的本机 HTTP/SSE 回归不访问付费供应商；真实模型测试需另行授权。

### 启动前的依赖自检

`scripts/probe_deps.py` 按 `pyproject.toml` 声明的**分发名**查 `importlib.metadata`，
只读元数据、不导入模块——导入 litellm 一个包就要好几秒，自检不该为它卡住启动。

```console
$ .venv/bin/python scripts/probe_deps.py
运行依赖齐全（12 个，Python 3.11，源码 0.24.3／已装 0.24.3）

$ .venv/bin/python scripts/probe_deps.py --toolkit
运行依赖齐全（12 个，Python 3.11，源码 0.24.3／已装 0.24.3）
可选工具包缺 3 个：pwntools gmpy2 z3-solver

$ .venv/bin/python scripts/probe_deps.py --json
{"python": "3.11.6", "runtime_missing": [], "toolkit_missing": [], "self_version": "0.24.3", "source_version": "0.24.3", "pip": true}

$ .venv/bin/python scripts/probe_deps.py        # editable 快照没跟上的情形
运行依赖齐全（12 个，Python 3.11，源码 0.24.3／已装 0.24.2）
提示：安装元数据落后于源码（起服务用 src/ 下的当前代码，不影响启动）
```

除依赖列表外还报三项：`self_version` 是本体的安装元数据版本（`null` 表示这个
环境里根本没装灵枢，`python -m spiritscout` 会直接找不到模块），`source_version`
是仓库源码里声明的版本，`pip` 表示还有没有 pip 可用（缺了就补装不了）。
`self_version` 缺失、`pip` 为假或有运行依赖缺失，退出码即为 1；元数据与源码版本
对不上只提示——editable 的 `.pth` 指向 `src/`，起的本来就是源码版本的代码。

缺运行依赖时退出码为 1，缺的包名逐行打印；`--json` 便于启动脚本消费。
本机启动器（`launch.cmd`）会在起服务前按「环境 → 依赖 → 配置 → 端口」
的顺序逐项查：

- **缺依赖 / 本体没装**：直接在仓库根执行 `pip install -e "SpiritScout"`，
  装完重新探一遍确认真的可用才继续启动；可选工具包同样自动补装，但装不上
  只警告不拦启动（缺的只是 CTF 工具链）。带 `-NoInstall` 则只报命令不动手。
- **依赖下载源**：默认国内镜像（清华 TUNA，`https://pypi.tuna.tsinghua.edu.cn/simple`），
  官方站在国内常常见底速；镜像装不下来时自动退 `https://pypi.org/simple` 重试一次，
  并把本次启动后续步骤都切到官方源。换源：`-PipIndex <url>`（优先级最高）或环境变量
  `SPIRITSCOUT_PIP_INDEX`；`-PipIndex official` 强制官方源；`-ShowPipIndex` 只打印
  当前解析出的源然后退出、不碰环境。裸词（`-PipIndex tuna`）直接报错，免得悄悄装到
  别的源上。
- **缺环境**（没有 venv、venv 里的解释器跑不起来、版本低于 3.11、或 venv 里
  没有 pip）：**只打印精确命令**，不代替用户建/删 venv——那属于影响面更大的
  操作。没有 venv 时会先看本机 `py -0p` 里有没有 3.11+，有就给出对应的
  `py -<版本> -m venv` 命令，没有才提示装 Python。

这样比进去跑半分钟才抛 `ImportError`、或等 uvicorn 报 `WinError 10048`
才发现上一次的控制台没退干净要省事。

### 环境自检脚本与桌面版（Windows）

`scripts/bootstrap.py` 是上面那套检查的跨平台版本，也是桌面版背后的那层：

```console
$ python scripts/bootstrap.py                  # 只体检，退出码 0 可用 / 1 需修复 / 2 没解释器 / 3 venv 坏了
$ python scripts/bootstrap.py --json          # 结构化结果，给 GUI / CI 消费
$ python scripts/bootstrap.py --fix           # 建 venv、补 pip、装缺的运行依赖
$ python scripts/bootstrap.py --fix --toolkit --recreate   # 连工具包一起，venv 坏了就重建
```

和启动脚本的分工：`start-local.ps1` 面向「已经建好 venv、只想双击跑起来」；
`bootstrap.py` 额外会**动手修**（建 venv、`ensurepip`、装依赖），也能跨平台跑。
它的装依赖顺序是清华 → 阿里 → 官方，逐源重试（每源带 `--retries 2 --timeout 30`），
`--mirror <url>` 可锁定单个源；解释器按「`--python` → venv 里已有的 → `py -0p` 里最低的
3.11+ → PATH」挑，避免拿到太新的 Python（gmpy2 / z3 常常只有源码包，自装会卡在编译）。

桌面版 `灵枢桌面版.exe` 就是它的 GUI 外壳：

```powershell
powershell -ExecutionPolicy Bypass -File SpiritScout\launcher\build-desktop.ps1
```

- 编译用 Windows 自带的 `csc.exe`（.NET Framework 4.x），**不需要 .NET SDK**；WebView2 的
  托管 DLL 与原生 loader 以资源编进 exe，首次运行解到 `%LOCALAPPDATA%\SpiritScout\lib`，
  写不进去就退程序目录、再退临时目录——所以产物只有一个约 824 KB 的 exe。
- 首次编译会从 NuGet 取 WebView2 SDK（约 8 MB，缓存在 `launcher/.cache/`）；之后
  `-SkipDownload` 即可离线编译。SDK 版本在脚本里写死：托管 DLL 与原生 loader 版本不一致
  会白屏，这类问题极难查。
- 端口被占会自动换下一个（8010 → 8011 …）；点「停止」或关窗口按进程树收，不留孤儿。
- 日志：`logs\desktop-<日期>.log`；崩溃：`crash-<时间>.log`（三处候选目录逐个试）。
- 内嵌浏览器起不来时**不算故障**：先探测 WebView2 运行时是否真的装了，profle 按「常用目录 →
  带进程号的兄弟目录 → 临时目录」逐级换着试（上一次的 `msedgewebview2.exe` 没退干净会独占
  常用目录，报 `0x800700AA`）；实在起不来就在窗口里画一张跟控制台同色的兜底卡片，同时用
  Edge 的 `--app=` 独立窗口打开同一个控制台——页面是同一份，排版样式一致。卡片上可以
  「重试内嵌浏览器」，成功就切回窗口里。设管理员密码会开一个真控制台窗口跑
  `--set-admin-password`（交互式输入必须有真终端）。
- 调试：设 `SPIRITSCOUT_WEBVIEW_DEBUG_PORT=9333` 启动，WebView2 会开一个 CDP 口，可以用
  Playwright `connect_over_cdp` 连上真窗口量样式、截图（`SPIRITSCOUT_WEBVIEW_DIR` 可指定
  profile 目录，两个一起用不会和用户正在开的窗口抢）。
- `bootstrap.py` 的体检结论要分开看：`ok: true` 才真能用；`probe: "missing"` 表示缺
  `scripts/probe_deps.py`（多半是把包裁剪过），这时说「依赖是否齐全」没有依据；
  `missing` 非空才是真缺依赖；`venv.has_pip: false` 需要 `--recreate` 重建。
- 装依赖时 `TMP` / `TEMP` / `PIP_CACHE_DIR` 一并钉到探测出来的可写目录（系统临时目录
  不可写就退到仓库根的 `.tmp/`），不会往别人家目录里散 wheel 缓存。

### 便携版（内嵌 Python，目标机器什么都不用装）

桌面版 exe 只是壳子，真正跑的是 Python 服务。要交给一台「没有 Python、也不该让人装 Python」的
机器，就把解释器和依赖一起打进去：

```powershell
# 1) 先出 wheel（便携版装的是 wheel，不是源码目录）
python -m build --outdir dist SpiritScout
# 2) 再打便携版目录 + zip
powershell -ExecutionPolicy Bypass -File SpiritScout\launcher\build-portable.ps1
```

出来的 `dist-portable\灵枢便携版-<版本>\` 长这样（约 334 MB，压成 zip 约 150 MB）：

```text
灵枢桌面版.exe      双击这个
desktop.json        告诉 exe：程序目录在哪、用哪个解释器（root=".", python="py\\python.exe"）
py\                 Python 3.11 embeddable + Lib\site-packages（灵枢与 95 个依赖）
configs\            system.yaml / models.yaml（模板）/ skills.yaml —— 第一次用先填模型渠道
data\ workspaces\ logs\
启动灵枢.cmd        想从命令行起就用它（按 936 代码页写，中文路径正常）
```

几个容易踩的点，脚本已经处理了：

- **embeddable 不吃 site-packages**：得把 `pythonXY._pth` 里的 `import site` 放开并补上
  `Lib\site-packages`，否则 `import` 全是 `ModuleNotFoundError`。
- **pip 会往用户目录跑**：解释器一旦被认为「用户 site 可写」，`pip install` 就装到
  `%APPDATA%\Python\Python311`（本机实测直接 `拒绝访问`，还会尝试卸载宿主机的同名包）。
  脚本用 `--no-user --target py\Lib\site-packages --upgrade` 钉住位置。
- **宿主机污染**：exe 给所有子进程设了 `PYTHONNOUSERSITE=1`，便携版只认自己那份依赖。
- **离线打包**：`-PythonZip <本地 python-3.11.9-embed-amd64.zip> -GetPip <本地 get-pip.py>`，
  内网机器也能出包。
- **配置只放模板**：`system.example.yaml` → `system.yaml`、`models.example.yaml` →
  `models.yaml`，真实渠道与密钥不会被打进包里。


### 单文件版（一个 exe，双击就开）

便携版是一整个目录；要「就发一个文件」就用单文件版：桌面版 exe（833 KB 的桩）后面拼上
运行时 zip（`py\` + `configs\`，约 131 MB），末尾 24 字节是 `[载荷长度][保留][SSRTPAY1]`。

```powershell
python -m build --outdir dist SpiritScout
powershell -ExecutionPolicy Bypass -File SpiritScout\launcher\build-portable.ps1   # 先出便携目录
powershell -ExecutionPolicy Bypass -File SpiritScout\launcher\build-single.ps1     # 再拼成单文件
```

产物 `dist\spiritscout-<版本>-single-win64.exe`（约 132 MB）。第一次双击时它自己：

1. 读尾部 24 字节拿到载荷偏移与长度（指纹取载荷前 64 KB 的 FNV-1a）；
2. 试三处可写目录：`%LOCALAPPDATA%\SpiritScout\runtime\<长度-指纹>` → exe 旁边的
   `灵枢运行时-<…>` → `%TEMP%\SpiritScout-runtime\<…>`；
3. 把载荷倒成 `runtime.zip`，用系统自带的 `tar.exe` 展开（Win10 1803+ 都有；没有就退到
   PowerShell 的 `Expand-Archive`），删掉 zip，写 `.ready` 认账；
4. 之后照便携版那套跑：内嵌 `py\python.exe` 起服务，界面还是那个 WebView2 窗口。

实测：首次启动 15 秒解完 322 MB / 19881 个文件，第二次启动 1.7 秒进就绪；换版本自然落到新目录，
旧目录可以手工删。三个形态（单文件 / 便携 / 仓库）同一个 exe 代码里按「有没有尾标载荷」自动选。


### 核对本地 LLM 端点

`scripts/check_local_llm.py` 从 `configs/models.yaml` 里挑出指向本机的供应商，
探测它的 `/v1/models`，把端点**实际返回**的模型 id 与配置里写的逐个比对：

```console
$ .venv/bin/python scripts/check_local_llm.py
供应商 本地  base_url=http://127.0.0.1:1234/v1
  端点可用，对外提供 2 个模型：
    lmstudio-community/bonsai-27b
    lmstudio-community/gemma-4-12b-it-qat
配置里指向这个端点的模型：
  ✓ lmstudio-community/bonsai-27b
全部匹配，可以直接用。
```

本地模型最常见的两个坑是服务没启动、模型名与端点返回的对不上（LM Studio 会把
目录名的 `-GGUF` 去掉并转小写）。对不上时脚本列出最接近的候选，改配置里的
`model` 即可；`--provider 名字` 可指定要查的供应商。

## Docker 构建

Windows、Linux、macOS 统一使用 Linux 容器，要求 Compose 2.20+。镜像使用 Debian
Bookworm 的 Python/Chromium，未强制 CPU 架构。本次验证 Windows 与 amd64 Linux；
macOS/ARM64 保留兼容代码路径，未完成实测。
Windows/macOS 安装 Docker Desktop 并启动；Linux 安装 Docker Engine 与 Compose 插件。
需要内核允许容器内的 bubblewrap/Chromium 命名空间，不能以宿主直跑替代沙箱。

推荐在仓库根目录执行 `python deploy.py up`（Windows 也可用 `py -3`，Unix 可用 `python3`）。
首次自动创建 `.env`，生成随机密码，不打印密码、不覆盖已有凭据。`doctor` 检查 Docker
与 Compose，`status` 查看状态，`logs` 跟踪日志，`down` 停服并保留卷。
没有 Python 时手动复制 `.env.example`、设置凭据，再运行 `docker compose up -d --build --wait`。

默认端口只绑定本机回环；应用带 HTTP 健康检查与优雅退出等待。镜像内保留源码，
不自动挂载整个宿主项目；修改代码、依赖后均需重新构建。数据保存在 Compose 项目隔离的卷：

| 卷 | 用途 |
| --- | --- |
| `spiritscout-data` | `.spiritscout/` 会话、审计、密钥、管理员和资源数据库 |
| `spiritscout-config` | 主配置、模型与编队配置；首次从镜像初始化，重建不覆盖用户配置 |
| `browser-profile` | 可选 SRC 浏览器的持久配置档案和登录态 |

Linux 数据卷避免 Windows/macOS 共享目录对 SQLite、文件锁和大量小文件的影响。
空配置卷会创建空的 `models.yaml`，随后从控制台添加模型。镜像构建排除本机 `.env`、
模型清单、编队配置、运行数据和工具缓存。构建期 apt/pip 下载使用缓存，并重试 apt 网络请求。

可以在 `.env` 中设置以下构建参数：

```dotenv
# 按需更换依赖源
PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple
# 安装 pwntools、z3、scapy、binwalk、sqlmap 等工具
INSTALL_TOOLKIT=1
```

修改后执行 `python deploy.py up`。端口冲突时可在 `.env` 中设置 `SPIRITSCOUT_PORT`
和 `SPIRITSCOUT_BROWSER_PORT`；多套部署同时使用不同端口及 `--project-name`。
Compose 默认使用 Docker 的 DNS，不强制指定公共 DNS；Linux Engine 也配置了
`host.docker.internal:host-gateway`，便于外接宿主 CDP 服务。

### 升级与数据迁移

旧版把项目目录挂进 `/app`，工作区仍在宿主 `.spiritscout/`。新版不会删除或自动接管
原数据；升级前需要迁移，否则新卷会呈现一个空工作区。先完成或停止运行中的任务，
关闭所有原生实例及旧容器，保留原目录作为备份：

```bash
docker compose --profile src-browser down
docker compose build spiritscout
python deploy.py migrate
python deploy.py up --no-build
```

`migrate` 以二进制流复制宿主 `.spiritscout/` 和 `configs/` 到对应卷，cmd 里直接跑，
不经过会损坏二进制归档的文本管道。目标数据卷必须为空，拒绝覆盖已有数据和归档链接；
原文件不改动。使用自定义 project name 时，迁移和启动都传相同的 `--project-name`。
迁移前必须停止其他项目名或原生进程中仍在使用原目录的实例，不能复制正在写入的数据库。

后续升级保留已有配置卷；上游主配置新增字段时，根据 `configs/system.example.yaml`
合并到卷内配置，不直接用模板覆盖模型配置。可用 `docker compose cp` 导入/导出配置。
备份请停服后导出三个卷，密钥与数据库必须一起保留。`down` 不删除卷，`down -v` 会删除卷。

### 显式源码开发模式

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build
```

开发覆盖将宿主源码、`configs/` 与 `.spiritscout/` 挂回容器；配置与数据不再来自生产卷。
Fedora 使用 `:z` 标记项目绑定目录；默认生产部署只使用命名卷，不需要重标记源码目录。
不要让原生与开发容器同时写同一个工作区。Windows/macOS 的共享目录性能较低，日常运行
优先使用默认数据卷。跨平台环境需各自创建 venv，不要把 Windows `.venv` 作为 Linux 工具层。

## 原生平台范围

| 环境 | 控制台、模型/资源管理、MCP | shell/Python 工具沙箱 |
| --- | --- | --- |
| Linux 原生 | 支持；安装 Python 3.11+，浏览器功能另需 Node.js 22+/Chrome | 默认 bwrap（需命名空间权限）；`sandbox_backend: host` 可退本机执行 |
| Windows 原生 | cmd `launch.cmd`；使用 `.venv/Scripts`、Windows 文件锁和 npm JS 入口 | 默认 host 后端（Git Bash + 项目 venv）；无文件系统隔离，见下节 |
| macOS 原生 | `launch.sh`；使用 `.venv/bin`，停止/重启使用系统 lsof | 默认 host 后端（`/bin/sh` + 项目 venv）；无文件系统隔离 |
| 三平台 Docker | 完整功能；可选 `src-browser` 人工操作页 | 在 Linux 容器内以 bwrap 执行，不退回宿主 |

### 本机 host 执行后端（Windows/macOS 不用 Docker）

`executor.sandbox_backend` 决定 shell/python 工具怎么跑，取值 `auto`（默认）/`bwrap`/`host`：

- `auto`：Linux 有 bwrap 就用 bwrap；Windows/macOS 没有命名空间能力，退 `host`；
  Linux 缺 bwrap 时**明确报错**，不静默降级（服务器请装 bubblewrap）。
- `bwrap`：强制命名空间沙箱，缺 bwrap 即报错。
- `host`：本机受限执行——工作目录锁在 `<session>/sandbox/`、环境变量按白名单重建
  （`HOME`/`TEMP` 指向会话目录、模型密钥等宿主变量不继承）、超时杀整个进程树、
  输出限幅并落盘。**它没有文件系统隔离**：进程仍能读宿主的其他可读路径，
  只适合本机自用、比赛机与研发验证。工具结果的 `parsed.sandbox` 会写明用的是哪个后端。

Windows 上的默认工具层：Git for Windows 的 `bash.exe`（自动从 `git.exe` 反推安装位置，
跳过不可用的 WSL 启动器 `System32\bash.exe`）+ 项目 `.venv\Scripts\python.exe`。
装齐 CTF 工具库：

```bat
.venv\Scripts\python.exe -m pip install -e ".[toolkit]"
```

`binwalk` 的 PyPI 包在 Python 3.11 上装得上但 `import binwalk` 会缺 `binwalk.core`；
固件/嵌套文件识别改用 `file_analyze`、`deep_strings` 与自写解包脚本。
macOS 可用 `SPIRITSCOUT_HOST_BASH=/opt/homebrew/bin/bash` 指定 shell。

Windows/macOS 原生控制台在 bwrap 不可用时不再直接报「沙箱不可用」，而是按上表走
host 后端；如需强制隔离，请用 Docker/WSL 部署并把 `sandbox_backend` 设为 `bwrap`。
Windows 的数据库执行锁位于 SQLite 自身锁区之外，不扩展文件，也保留硬链接别名互斥。
进程启动和超时清理使用各平台入口，npm/npx 在 Windows 通过 Node.js 的 JS CLI 执行，
不把任务参数拼入 `cmd.exe`。Chrome 自动查找 PATH 与 Windows/macOS 标准应用位置，
仍可用 `SPIRITSCOUT_CHROME_EXECUTABLE` 指定其他路径。

CI 覆盖 Linux 全量回归、Windows 原生兼容用例，以及 amd64 Linux 镜像构建。
这些检查不等于已在所有主机、Docker 安全策略或第三方浏览器上完成实际任务测试。

### 签名启动器（Windows 双击入口）

Windows 上双击 `.cmd` 时"未知发布者"来自两处：文件带了网络标记（第 1 类），或者入口没有
Authenticode 签名（第 2 类）。先分清是哪种：

```powershell
# 有输出 = 带网络标记；去掉就能消除提示，不需要证书
Get-Item .\启动服务.cmd -Stream Zone.Identifier -ErrorAction SilentlyContinue
Unblock-File .\启动服务.cmd
```

`.cmd` / `.bat` **没有 Authenticode 容器**，`Set-AuthenticodeSignature` 直接拒绝：

```text
StatusMessage : The form specified for the subject is not one supported or known by the specified trust provider
```

要让双击入口带上发布者，入口必须是 PE 文件。仓库自带一个启动器源码和构建脚本：

```powershell
# 首次：生成自签名证书、装进当前用户的信任存储、下载便携版 osslsigncode、编译并签名
$env:SPIRITSCOUT_SIGN_PASSWORD = "自己定的 pfx 密码"
pwsh -File SpiritScout\launcher\build-launcher.ps1
# 之后改完源码重建（密码沿用同一个）
pwsh -File SpiritScout\launcher\build-launcher.ps1 -PfxPassword "自己定的 pfx 密码"
```

产物是仓库根目录的 `启动服务.exe`，行为与 `启动服务.cmd` 完全一致（UTF-8 代码页、
缺 key 提示、前台调 `start-local.ps1`、退出后停窗）。验证：

```powershell
Get-AuthenticodeSignature .\启动服务.exe   # Status 应为 Valid，SignerCertificate 是自己签的 CN
```

材料位置与边界：

| 项 | 位置 | 说明 |
|---|---|---|
| 证书与私钥 | `%USERPROFILE%\.spiritscout\signing\SpiritScoutLocal.pfx` | 不入库；密码由 `-PfxPassword` / `SPIRITSCOUT_SIGN_PASSWORD` 提供 |
| 公钥证书 | 同目录 `SpiritScoutLocal.cer` | 已装进当前用户的「受信任根」「受信任发布者」 |
| 签名工具 | 同目录 `osslsigncode.exe` | 缺失时脚本自动下载便携版，不要求 Windows SDK |
| 编译产物 | 仓库根 `启动服务.exe` | 已进 `.gitignore`，换机器重建即可 |

自签名证书只在**本机**有效：链的终点是自己装进用户信任存储的那张证书，换机器、换用户
都要重跑一次构建脚本重新信任。对外分发（给别人双击）仍需 CA 签发的代码签名证书，
自签名换不来 SmartScreen 声誉——它消除的是"未签名/未知发布者"，不是"没下载量"。

`启动服务.cmd` 继续保留：它是命令行入口，任何环境都能用，签不签名都不影响运行。
签名脚本本身必须存成 **UTF-8 with BOM**——Windows PowerShell 5.1 读到无 BOM 的 `.ps1`
会按 ANSI 解码，中文注释会直接变成 `Unexpected token` 语法错误。

## 本地模型

`local-llm` MCP 把本机推理端点接成三个工具交给 agent：看后端状态、列模型、单轮提问。
模型跑在自己机器上——提问不出网、不计费，适合摘要、改写、批量分类这类廉价活，把贵的
云端模型留给真正需要判断的环节。

后端走 OpenAI 兼容协议，LM Studio 和 Ollama 都能直接对上：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `SPIRITSCOUT_LOCAL_LLM_URL` | `http://127.0.0.1:1234/v1` | LM Studio；换 Ollama 用 `http://127.0.0.1:11434/v1` |
| `SPIRITSCOUT_LOCAL_LLM_MODEL` | 空 | 默认模型名；留空用端点上的第一个 |
| `SPIRITSCOUT_LOCAL_LLM_TIMEOUT` | `120` | 单次请求硬顶（秒） |
| `SPIRITSCOUT_LOCAL_LLM_KEY` | 空 | 端点要令牌时用，按 `Authorization: Bearer` 发 |

配置里默认 `enabled: false`：先把后端起起来（LM Studio 点 Start Server 或 `lms server start`，
Ollama 是 `ollama serve`），再到控制台「设置 → MCP 接入 → local-llm」打开。关掉就整条从
agent 的工具目录里消失，配置原样留着。

它标 `default_risk: readonly`、`scope_enforcement: none`——只问本机模型，不碰目标系统，
也不触网。连不上时工具会直接说清是「后端没起」还是「地址配错」，并附上对应的下一步命令。

### 本地 MCP 模板

「设置 → MCP 接入 → 添加」的编辑框顶部多了一个**本地 MCP 模板**下拉：选中就
把 `transport` / `command` / `args` / `default_risk` 填好，只需要替换占位符。

| 模板 | 启动方式 | 要换的占位符 |
| --- | --- | --- |
| 文件系统 | `npx -y @modelcontextprotocol/server-filesystem {ROOT}` | `{ROOT}` 允许读写的绝对目录 |
| 记忆库 | `npx -y @modelcontextprotocol/server-memory` | 无 |
| 顺序推理 | `npx -y @modelcontextprotocol/server-sequential-thinking` | 无 |
| 时间与换算 | `uvx mcp-server-time` | 无 |
| 网页抓取 | `uvx mcp-server-fetch` | 无（走代理填 `HTTPS_PROXY`） |
| 仓库操作 | `uvx mcp-server-git --repository {REPO}` | `{REPO}` 仓库路径 |
| SQLite 查询 | `uvx mcp-server-sqlite --db-path {DB}` | `{DB}` 库文件路径 |
| 本项目 venv | `{PYTHON} -m {MODULE} --stdio` | `{PYTHON}` 解释器、`{MODULE}` 模块名 |
| 自定义 | 空 | 自己填 |

本机没装 `npx` / `uvx` 的模板在下拉里是灰的，并标出缺哪个——不让填完才在调用时报错。
模板只描述**怎么启动**，不预置任何密钥：需要令牌的服务把值填在「环境变量」字段，
走加密密钥库，不进 `configs/system.yaml`。

保存后的接入对**新启动的会话**生效，正在执行的 MCP 连接不会被热替换。

## 浏览器

`chrome` MCP 按用户选择的任务模式装配：智能体/CTF 模式使用会话独立的无头浏览器，
无需启动 CDP 调试端口，也不读取用户已有登录态；SRC 模式连接现有浏览器复用登录态。
工具注册前会验证真实浏览器连接，连接失败会留痕并跳过，不将握手成功误报为浏览器可用。

源码自动解题环境需安装 Chromium 或 Google Chrome；可通过
`SPIRITSCOUT_CHROME_EXECUTABLE` 指定浏览器可执行文件。Docker 镜像包含 Chromium。
以下 CDP 配置与人工接管说明仅适用于 SRC 模式。

Playwright 每起一次浏览器，会在会话目录的 `browser-output/tmp` 下落一份 Chromium
档案（`GrShaderCache`、`BrowserMetrics-spare.pma` 这类），单份 10–20 MB 且不会
自己消失。会话收尾时会看一眼这一层，**累计超过 64 MB 才清**；只清 `tmp`，同级的
截图、console 日志和下载文件不动。阈值用 `SPIRITSCOUT_BROWSER_TMP_PRUNE_MB` 调整，
写 `0` 表示每次退出都清。要立刻回收历史残留，把该变量临时设为 `0` 再跑一个会话即可。

### SRC 可选：随 Docker 部署可操作浏览器

项目包含 Chromium、虚拟桌面与 noVNC，按需启用 `src-browser` profile：

```bash
docker compose --profile src-browser up -d --build --wait
```

准备好 `.env` 中的控制台密码后执行上述命令，等待浏览器健康检查通过再下发 SRC
任务。控制台地址为 `http://127.0.0.1:10010`，浏览器操作页为
`http://127.0.0.1:10011`，两者使用 `.env` 中配置的管理员用户名和密码。
收到登录、验证码或滑块提问时，在操作页完成后回会话回复「已完成」。

默认 `docker compose up -d --build` 只启动主服务，智能体/CTF 的无头浏览器在主服务内
独立运行。共享浏览器不作为主服务的启动依赖；其故障不阻止主服务启动。
启用 profile 后，SRC 默认通过 Compose 内网的 `http://browser:9223` 连接浏览器。
CDP/VNC 不发布到宿主机，两个网页端口只绑定本机回环；远程使用时可通过 SSH 转发
`10010`、`10011`，或配置支持 WebSocket 的 HTTPS 反向代理。

SRC 浏览器的持久登录态保存到 Docker 卷 `browser-profile`，重启和重建容器后保留；
`docker compose --profile src-browser down -v` 会删除该卷。不同 SRC 会话共享这个
浏览器，避免同时操作同一页面；智能体/CTF 的隔离浏览器不读取这个卷。
内置浏览器为标准 Chromium，不含商业指纹管理能力。首次构建需要联网下载依赖。

Fedora 等启用 SELinux 的主机在开发模式使用项目挂载的 `:z` 选项设置容器共享标签；浏览器日志
直接输出到标准错误，不通过 `/dev/stderr` 的 proc 路径创建日志文件。无需关闭 SELinux
或导入宽泛的放行策略。该挂载会重标记当前项目目录，源码与运行数据仍保存在宿主机。

### SRC 可选：已有 Chrome / 指纹浏览器

`chrome` MCP 通过 Playwright 连接已有浏览器的 CDP 调试端口，
复用该浏览器的配置档案和登录态。收到 Agent 提问后，在原浏览器窗口完成登录、验证码或滑块，
回到会话回复，Agent 会继续执行。

- `configs/system.yaml` 已启用 `chrome`，原来的无头 `playwright` 改为可选关闭。
  默认授权给业务体验 Agent 与 CTF Web Agent，其他支持动态 MCP 的角色可在
  `allowed_agents` 中显式加入；SRC 危险操作仍需逐次审批。
- 先确认外部浏览器的 CDP 调试端口可达。使用转发器时，也要确认转发器已启动。
- 使用外部浏览器时，在 `.env` 中设置
  `SPIRITSCOUT_CHROME_CDP_URL=http://实际可达IP:9223`，无需启用 `src-browser` profile。
  Docker 会自动解析 `host.docker.internal` 为 IP；源码部署在 WSL 中使用自己的默认
  网关，其余环境使用本机回环。不能把 WSL 网关直接当成 Docker 网关。
- Docker 镜像内置 Node.js 22、Chromium 和固定版本的 MCP，无需在运行时下载浏览器。源码部署
  需安装 Node.js 22+；默认通过 npx 安装固定版本，已有 MCP CLI 时可设置
  `SPIRITSCOUT_CHROME_MCP_CLI` 为其 `cli.js` 路径。
- `--caps storage` 提供 `mcp__chrome__browser_cookie_list` 等 Cookie 工具，能读取
  HttpOnly Cookie；不要用 `document.cookie` 代替完整登录态读取。手动完成验证后，
  在会话提问处回复 Agent，由它重新检查页面与 Cookie。

该接入使用的是共享的浏览器配置档案，登录态会随原浏览器保存；它不提供会话之间的
自动隔离。同一浏览器应由一个任务操作，避免与其他 Agent 同时控制同一页面。
指纹配置由原浏览器提供，灵枢不改写浏览器指纹、代理或已有配置。

### 外部浏览器的启动与人工接管

1. 启动外部浏览器及所需的 CDP 转发器，保留浏览器窗口供手动操作。
2. 在项目根目录执行 `docker compose up -d --build spiritscout`，打开
   `http://127.0.0.1:10010`。源码部署按 README 启动，另需准备 Node.js 22+。
3. 在 SRC 模式下向业务体验 Agent 下达浏览器任务，例如：
   「打开已授权站点，遇到登录或验证码时提问等我操作，完成后重新读取登录态再继续。」
4. 收到 Agent 提问后，在外部浏览器中完成登录、验证码或滑块，再在会话中
   回复「已完成」。Agent 会重新检查页面和 Cookie，确认成功后继续；浏览器中的变化
   在下一次工具读取时可见，不会自动推送 Cookie。

截图等浏览器产物写入当前会话的 `workspace/browser-output/`。Cookie 属于登录凭据，
只在当前任务需要时读取，避免复制到项目记忆、报告或聊天分享中。

### 连接排查与升级说明

- 若 SRC Chrome MCP 不可达，先在实际运行灵枢的环境中访问
  `http://实际可达IP:9223/json/version`，确认返回浏览器版本与
  `webSocketDebuggerUrl`；Windows 本机连通不代表 WSL 或 Docker 内也能连通。
  修正转发器或 `SPIRITSCOUT_CHROME_CDP_URL` 后重新启动服务。
- 源码首次使用需通过 npx 下载固定的 `@playwright/mcp@0.0.83`；离线环境可预装
  并用 `SPIRITSCOUT_CHROME_MCP_CLI` 指向运行环境内可访问的 `cli.js`。
- 升级已有部署时需重建 Docker 镜像以加入 Node.js、Chromium 与 MCP；SRC 内置
  可操作浏览器用 `docker compose --profile src-browser up -d --build --wait` 构建启动。
  使用自定义配置的用户请参考 `configs/system.example.yaml` 添加并启用 `chrome`；原无头 `playwright`
  可按需保留，但它不共享这个 Windows 浏览器的登录态。

共享资源默认保存于 `<workspace>/resources/`，可用 `resources.root` 指定持久目录。
`resources.freshness_hours` 控制“近期观测”提示（默认 24 小时），不会把历史标记为本次已验证。
`resources.npm_registry` 默认为 npm 官方仓库，可指向组织内仓库。MCP 配置变更对
新启动的会话生效，运行中的连接不会被替换；Skill 在下一次参考检索时读取当前版本。

模型默认使用 `prompt_caching: provider_default`，不附加缓存参数。确认端点支持
Anthropic Messages 显式缓存后，可在模型编辑页选择 `anthropic_ephemeral`。
可按实际美元报价配置 `cost_cached_input_per_mtok` 与 `cost_cache_write_per_mtok`；
未配置缓存单价时费用仍按普通输入单价估算。缓存命中收益需以端点实际返回用量评估。

## 技能库

内置的 206 条安全技能在 `src/spiritscout/knowledge/data/security_skills.json`，随代码走。
自己加的技能不要只留在资源库里——`catalog.db` 挂在工作区下，工作区重建（换机器、
删 `data/workspace`、重置状态根）会把它一起带走，页面上那些条目就凭空消失。

自定义技能的真源是 `configs/skills.yaml`：控制台每次启动把它同步进资源库的
`settings` 表（只增改、不删；内容一致时跳过写入）。字段与「技能」页一致：
`skill_id` / `domain` / `description` / `body` / `severity` / `cwe` / `tools` /
`source` / `path` / `enabled`。

```bash
# 把一堆带 frontmatter 的 SKILL.md 收进清单（目录结构 skills/<domain>/<id>/SKILL.md 也行）
python -m spiritscout.resources.skill_sync import <目录或单个 SKILL.md>

# 把资源库里现有的自定义技能倒回清单（换机器前先导出一次）
python -m spiritscout.resources.skill_sync export

# 只做同步（等价于控制台启动时那一步）
python -m spiritscout.resources.skill_sync sync
```

`import` 会合并进现有清单，同 `skill_id` 以新文件为准；导入和导出都写同一个文件，
所以它能提交、能打包——便携包会把 `configs/skills.yaml` 一并放进去。

### 仓库里的技能包

仓库带了两个目录，都不是运行时依赖，是内容的存放地：

| 目录 | 内容 | 体积 |
| --- | --- | --- |
| `skills/pack/` | 打包好的 85 个 skill，一个目录一个 skill（`<id>/SKILL.md` + 自带 references / scripts / payloads），另有 `install.ps1` 与 `清单.md` | 78.9 MB |
| `skills/sources/` | 上面那批的原料：Hello-CTF、Des-CTF-Knowledge、CTF-md 文档大全、无敌逆向渗透 skills 等 | 125.8 MB |

**这两个目录不入库**（`.gitignore` 已挡），只在本地保留：它们合计 205 MB、4850 个文件，
且含大量真实赛题答案与第三方题解原文。运行时读的是 `configs/skills.yaml`——那里面已经把
这些技能的正文内联成 `body` 字段，删掉这两个目录不影响任何功能，只是无法再跑下面的 `import`。

目录结构是平铺的（`skills/pack/ctf-web/SKILL.md`），导入时要限定文件名：

```bash
# 只收 SKILL.md：每个 skill 目录都带一堆 references/*.md，全收进来会变成几百条碎片技能
python -m spiritscout.resources.skill_sync import skills/pack --only SKILL.md

# 导进资源库（等价于控制台启动时那一步），再刷新「技能」页
python -m spiritscout.resources.skill_sync sync
```

导入结果：85 条，`configs/skills.yaml` 约 0.75 MB（正文内联，不依赖 `skills/` 在不在）。
两处重复的 `SKILL.md`——`ash12-elf-complete-flow`、`src-hunter`——在包里各有一份顶层副本
和一份子目录副本，内容逐字节相同，按 `skill_id` 合并成一条。

`skills/` 下的 `.git` / `__pycache__` / `*.pyc` 不入库：`Hello-CTF` 自带 196 MB 对象库、
`Des-CTF-Knowledge` 30 MB，都是上游仓库历史和已编译缓存，跟技能内容无关；单个 pack 文件
（195.86 MB）也超过 GitHub 100 MB 的单文件上限。版本历史留在原目录 `~/.dsh/skills` 里。

自定义 MCP 可用 `allowed_agents` 指定额外执行角色，例如 `[business_context, ctf_web]`（当前支持业务体验和 CTF 各执行角色）；空列表沿用原有工具范围。该配置不会授予灵枢、秘书或报告角色执行权限，也不会扩大任务授权范围，工具审批仍按会话模式执行。

## 搜索与费用

SRC 和普通 CTF 的 `web_search` 优先复用有效缓存，再使用 Exa 官方免密搜索；免费服务不可用时，通过 curl 获取公开搜索引擎结果。模型也可设置 `source: public` 直接使用公开引擎，并在关键词中组合精确短语、`site:` 和版本/错误特征。公开结果的时效与适用版本仍须核对。

付费 Exa API 仅用于特别困难且明显阻塞进度的问题。模型须基于实际证据自行判断，显式给出 `paid: true` 和 `blocker`，说明已尝试的方法、免费资料为何不足以及关键缺口如何影响下一步。免费额度耗尽、限流或普通查询失败不会自动触发付费请求；有效的旧付费结果可以免费复用。MCP 管理页保存的密钥只供这一受控路径使用。智能体模式禁止所有上述网页搜索路径。

搜索输出先在本地去除 HTML 脚本/样式/导航噪声、重复段落和追踪参数，再合并重复 URL，返回固定字段的紧凑 JSON（每条摘要最多 480 字符，整份最多 4,800 字符）。缓存命中逐字复用结果正文；旧版已付费缓存就地清理并保留原检索时间，格式升级不触发重新检索。缩短结果降低输入量，实际模型缓存命中率仍以端点返回用量为准。

## 数据与备份

用量逐笔写入**基础工作区**的 `usage.db`（SQLite WAL 事务）。会话工作区
（`sessions/<id>/`）会随归档与清理一起消失，账本落在那里的话，「用量」页读的共享库
就永远是 0——题跑完了、token 花掉了，页面上什么都没有。首次打开时导入旧
`usage.json` 并保留原文件；备份运行中的数据库请使用 SQLite 备份接口，
或停服后复制。读取结果按数据库/WAL 文件版本缓存，单文件仅保留最新快照。

控制台每次启动、以及删除会话之前，都会把会话目录里遗留的 `usage.db` 并回共享库
（按 `call_id` 去重，可重复执行无需担心重复计）；`experience.db` 走同一套并库逻辑，
所以老工作区升级上来不会丢历史。

模型注册表 `configs/models.yaml` 由「模型」页写回时会先留一份
`models.yaml.bak-<时间戳>`。手滑删掉一个供应商、或者某条异常路径把它写成空清单，
从备份取回即可；这些备份不进仓库。

资产库启动导入按历史记录游标增量执行；`POST /api/assets/sync` 可全量重扫历史会话。
会话列表与状态由单一调度器兜底刷新，隐藏页面降频，SSE 继续提供即时事件。
