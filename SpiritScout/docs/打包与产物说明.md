# 打包与产物说明

这份文档讲一件事：**`packages\` 里那些文件是什么、给谁用、拆开长什么样、怎么确认它是完整的。**

如果你只想知道「怎么用」，看包内的 `使用说明.txt` 就够了。这份是给维护者、交付方、
以及第一次拿到包想弄清里面有什么的人看的。

## 一、三种产物，各给一种人

| 产物 | 给谁 | 对方需要什么 |
| --- | --- | --- |
| `SpiritScout-<ver>-portable.zip` | **最终用户**。不想碰命令行、不想装 Python | 64 位 Windows，解压即可 |
| `spiritscout-<ver>-py3-none-any.whl` | 已装好 Python 的开发者，或要接进自己环境的运维 | Python 3.11+ |
| `spiritscout-<ver>.tar.gz` | 要审源码、或从源码构建的人 | Python 3.11+ 与编译工具链 |

**发给人用就发 zip。** wheel 和 sdist 是给开发者的，普通用户拿在手里没有意义——
装上之后还是要自己配 Python 环境，不如直接用便携包。

## 二、便携包的结构

解压后是这样一个目录（版本号和包名一致）：

```
SpiritScout-0.24.1-portable\
├── 1-启动服务.bat          双击这个
├── 2-停止服务.bat          按端口收口，含残留进程
├── 使用说明.txt            给终端用户的一页说明
├── runtime\                解释器与全部依赖（约 655 MB）
├── app\                    程序本体（约 5.5 MB）
├── configs\                配置模板与当前配置
└── data\                   运行数据（会话、报告、经验库）
```

四个目录的分工是清晰的：`runtime` 是「能跑起来的前提」，`app` 是「程序」，`configs`
是「怎么跑」，`data` 是「跑出来的东西」。**只有 `data\` 是你的数据，其余都可以在重装时
被覆盖。**

### runtime\ —— 为什么占了 655 MB

```
runtime\
├── python.exe              解释器本体（CPython 3.11，64 位）
├── python311.dll
├── *.dll                   VC 运行库等
├── DLLs\                   标准库的 C 扩展
├── Lib\
│   ├── *.py                标准库（已按需精简）
│   └── site-packages\      第三方依赖
└── Scripts\
```

`runtime\` 是**一个完整的 Python 安装**，而且 `python.exe` 就在这一层的根上——这是有意的：
CPython 用「`python.exe` 所在目录」当作 `sys.prefix`，所以把整个目录搬走、改名、放到中文
路径下都能正常工作，不需要任何环境变量。

`Lib\site-packages\` 里是全部依赖，重的那几个是：

- **CTF 工具链**：`pwn`（pwntools）、`z3-solver`、`gmpy2`、`scapy`、`capstone`
- **模型调用**：`litellm` 及其依赖树
- **Web**：`fastapi`、`uvicorn`、`starlette`
- **数据**：`numpy`、`pydantic`、`sqlite` 相关

构建时会剥掉两类东西，别手工加回来：

1. **包自带的 `tests/` 目录**（99 个包里有），对运行无用；
2. **`__editable__*.pth` 与 `spiritscout-*.dist-info`** ——如果留着，包内的程序会顺着
   这些文件去连**构建机上的源码路径**，到别人机器上直接 import 失败。

### app\ —— 程序本体

```
app\
├── src\spiritscout\        真正的代码
├── docs\                   项目文档（含本文件）
├── scripts\                运维脚本
├── pyproject.toml
├── README.md
├── CHANGELOG.md
├── SECURITY.md
├── LICENSE
└── .env.example
```

代码是**以源码形式**放在这里的（不是装进 site-packages），启动时通过 `PYTHONPATH` 指过去。
这样做的好处是现场能直接改、直接看，出问题不用先解包。

内置的两份知识库也在这一层：

| 文件 | 内容 |
| --- | --- |
| `src\spiritscout\knowledge\data\security_skills.json` | 各方向手法索引（约 645 KB） |
| `src\spiritscout\knowledge\seed.py` | 平台特性、载荷形态、常见坑位 |

### configs\ —— 配置

| 文件 | 作用 |
| --- | --- |
| `system.yaml` | 当前生效的系统配置（路径已改写为 `data/workspace/...`） |
| `system.example.yaml` | 带完整注释的模板，改配置前对照它 |
| `models.yaml` | 模型注册表，**`api_key` 全空**，装好后在控制台里填 |
| `models.example.yaml` | 模型配置模板（6.8 KB，字段说明都在里面） |
| `models.mock.yaml` | 不用真模型时的假配置，用于本地跑通链路 |
| `agent_models.yaml` | 各专项 Agent 用哪个模型 |

**`system.yaml` 里的五个路径键在打包时被改写成 `data/workspace/...`。** 这一步是构建脚本
用正则做的，每一处必须命中恰好一次，否则构建直接失败——避免「某个路径没改到，运行起来
往构建机上写」这种坏包。

### data\ —— 运行数据

```
data\
├── 说明.txt
└── workspace\
    └── experience.db       预置的做题经验（50 条，36 KB）
```

**出厂包里没有任何凭据。** `admin.db`（管理员 scrypt 哈希）、`auth.key`（登录 Cookie
签名密钥）、`vault.db` + `vault.key`（供应商 Key）都是你本机第一次启动后才生成的：
`build_release.py` 组装时先把它们清掉，`make_zip()` 之前再断言一次 `data\` 里没有，
命中就删掉并中止出包。所以「包里带了个默认密码」这种事不会发生——密码是解压的人自己
在首次启动时设的。

这是**出厂状态**。真正跑起来之后会自己长出下面这些：

```
data\workspace\
├── blackboard.db           会话与任务数据
├── knowledge.db            知识库
├── experience.db           做题经验（预置 + 每轮收尾自增长）
├── audit.jsonl             审计流水
├── chroma\                 向量库
├── reports\                全局报告
├── resources\              资源库
├── uploads-staging\        上传暂存，提交后转进会话
├── admin.db                管理员账号（scrypt 哈希）＋登录会话
├── auth.key                登录 Cookie 的 HMAC 签名密钥（首次签发会话时生成）
├── vault.db + vault.key    加密的供应商 Key 与主密钥
└── sessions\
    └── sess-xxxxxxxx\
        ├── meta.json
        ├── bb.db                该会话的黑板
        ├── audit.jsonl          该会话的审计
        ├── attachments\         你上传的题目文件，原样保存
        ├── artifacts\           解题中间产物
        ├── reports\             报告与 WP
        └── sandbox\             沙箱执行目录
```

**备份就拷 `data\` 整个目录。** 但注意 `vault.key` 必须和 `vault.db` 一起走——只备份数据库
不备份 key，恢复后所有供应商 Key 都解不开，得重新填。

**想恢复成刚装好的状态，删掉 `data\` 即可**，下次启动会重建。唯一会丢的是经验库和会话
记录，不介意就没有副作用。

## 三、启动脚本做了什么

`1-启动服务.bat` 不是简单的一行命令，它处理了便携场景的几个坑：

```bat
cd /d "%~dp0"                                    ← 先切到包根，配置路径全是相对 CWD 的
runtime\python.exe -m spiritscout --set-admin-password --if-missing ^
                    --config configs\system.yaml  ← 还没有管理员就先问你设密码
set VIRTUAL_ENV=%~dp0runtime
set PYTHONPATH=%~dp0app\src
set PYTHONUTF8=1                                 ← 中文路径与中文输出
set PYTHONNOUSERSITE=1                           ← 不读宿主机的用户 site-packages
set LITELLM_LOCAL_MODEL_COST_MAP=True            ← 不联网拉价格表
runtime\python.exe -X utf8 -m spiritscout --config configs\system.yaml --port 8010
```

两个环境变量值得单独说：

- **`PYTHONNOUSERSITE=1`**：不加这个，如果对方机器上恰好有个 `%APPDATA%\Python`，
  Python 会把它也挂进 `sys.path`，装过的旧版本包可能盖掉包内的代码。
- **`LITELLM_LOCAL_MODEL_COST_MAP=True`**：litellm 默认会去拉远端价格映射表，内网或断网
  环境下会卡住几十秒。置成 True 用包内自带的。

**首次设密这一步也是包内的产品代码**：`--set-admin-password` 输两遍（输入不回显），
只把 scrypt 加盐哈希写进 `data\workspace\admin.db`；明文不进命令行、不写日志、不落盘。
**密码不设长度限制**（一位也行，整句话也行），设完在终端里把明文显示一次方便记下来，
之后重启、日志、界面都不再显示。已有账号就跳过（`--if-missing`），不是交互终端
（脚本、CI、管道）也跳过，绝不卡住启动。回车两次等于「不设密码」，控制台只绑
`127.0.0.1`。

**`cd /d "%~dp0"` 不能省**：`configs/system.yaml` 里所有路径都是相对当前工作目录的，
从别的目录启动会读到错误的相对路径。

## 四、一个包是怎么造出来的

三步，顺序不能换：

```bash
python _work/build_release.py              # 1) 组装暂存目录
python _work/validate_release.py           # 2) 冒烟验证，跑完自清场
python _work/build_release.py --zip-only   # 3) 打 zip
```

**为什么 zip 一定排在最后**：第 2 步会把控制台真正起一次，`data\workspace\` 下会多出
`resources\`、`sessions\` 之类的运行痕迹。先打 zip 就等于把「被人点开过一次」的包发出去。
所以验证脚本验完自己清场，再打 zip。

构建过程里几个关键动作：

| 动作 | 为什么 |
| --- | --- |
| 复制 CPython 基础层到 `runtime\` | 对方不用装 Python |
| 从 `.venv` 复制依赖到 `runtime\Lib\site-packages` | 版本与本机验证过的一致 |
| 剥 99 个包自带的 `tests/` | 省体积，运行用不到 |
| 剥 `__editable__*.pth` / `spiritscout-*.dist-info` | 否则包内 import 回连构建机路径 |
| 标准库按 `STDLIB_DROP` 精简 | 再省一截 |
| 正则改写 `system.yaml` 里的五个路径键 | 让数据落在 `data\workspace\` |
| 复制 `experience.db` 进 `data\workspace\` | 让包带上做题经验 |
| 清 `admin.db` / `auth.key` / `vault.*`，zip 前再断言 | 本机凭据不进包，密码由解压的人自己设 |
| 出包前剪 `app\**\__pycache__` | 验包起控制台时会写回自己的 `.pyc`，别打进发布包 |
| 生成 `使用说明.txt` 与两个 bat | 终端用户不看 docs |

## 五、怎么确认这个包是完整的

拿到包之后，按这个顺序自检（都不需要装额外东西）：

**1. 文件数对不对**

```bat
dir /s /b /a-d | find /c /v ""        rem 0.24.3 实测 25621 个文件（另有 3404 个目录，解压后 619 MB）
```

zip 里的条目数是 25621（约 212 MB）——zip 不单独记录目录条目。

**2. 校验和比对**

```bat
certutil -hashfile SpiritScout-<ver>-portable.zip SHA256
```

和发布方给的 SHA-256 对照。注意**自己重新打的包哈希一定不同**——zip 会记录文件时间戳，
同样的源码在不同时刻打出来字节就不一样。哈希只用于确认「你拿到的和我发出的是同一个文件」，
不用于确认「内容正确」。

**3. 直接起一次**

```bat
1-启动服务.bat
```

看到控制台地址后浏览器打开，能出登录页就说明解释器、依赖、配置、模板、数据库五层都通了。
**这一步最能说明问题**，比任何静态检查都准。

如果起不来，按这个顺序排查：

| 现象 | 多半是 |
| --- | --- |
| 窗口闪一下就没了 | 路径含特殊字符，或 `runtime\` 被解压工具截断 |
| 提示端口占用 | 已有实例在跑，先双击 `2-停止服务.bat` |
| 起来但页面 404 | `app\src` 不完整，重新解压 |
| 页面能开但模型报错 | `configs\models.yaml` 里 `api_key` 还是空的，去控制台填 |

## 六、几个容易被误解的点

**「为什么 229 MB 的 zip 解压出来 655 MB？」**
因为压缩对象主要是 Python 依赖里的 `.so`/`.pyd`/`.py`，压缩比普遍在 3 倍左右。这个体积是
正常的，不是塞了垃圾。

**「能不能不打包 runtime，让用户自己装 Python？」**
可以，那就是 `pip install` 路线（wheel）。便携包存在的意义恰恰是**不让用户碰 Python**——
目标用户里相当一部分机器上装着三四个版本的 Python，装错版本比不装更麻烦。

**「`data\` 里为什么预置了经验库？」**
包是给「打 CTF」的人用的，经验库记的是判读规则（比如「连接超时在按需实例上应该先当成
实例生命周期信号，而不是目标防护」），不是解题步骤。预置一批能让第一次用的人不至于从零
攒判断。不想要就删掉 `experience.db`，下次启动重建空库。

**「包里的 `configs\system.yaml` 和仓库里的一样吗？」**
不一样。包内那五个数据路径被改写成了 `data/workspace/...`，其余字段相同。所以**别把包内
的 config 直接拷回仓库**，会把数据写到包的目录里去。
